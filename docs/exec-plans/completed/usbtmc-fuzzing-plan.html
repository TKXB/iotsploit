USB response handling belongs to the harness. The MCU monitor independently judges faults, lockups, halts and resets. A running CPU can still have an unusable USBTMC interface.

Locked scope for the proposed implementation

  • Python owns campaign USB access on the rig. Flutter uses backend discovery, not desktop-local enumeration.
  • One transport and one harness support both modes. No new campaign engine or generic sequence framework.
  • The fuzzer keeps zero dependency on iotsploit-core and Django. Composition supplies the interface and existing resource lease.
  • Linux is the first hardware qualification target. Existing Nordic and STM32 Cortex-M targets can use the current MCU monitor. ESP32-S3 needs a separate monitor backend.
  • The Rust desktop control session remains, with same-host resource coordination. Separate machines' local lock files do not coordinate each other.
  • Initial campaigns stop on failure. Automatic recovery is deferred until evidence preservation and reconnect behavior are proven.

4. Configuration, execution and replay contracts

Proposed campaign configuration

    "sequence": [

    ]
  },
  "monitors": [{
    "kind": "mcu_core", "name": "mcu_core:main",
    "resource": "usb:0483-PROBE_SERIAL/debug", "target": "STM32F407VG",
    "options": {"recovery_policy": "stop", "settle_ms": 20}
  }]
}

Identity values are placeholders. Derive endpoints from the selected interface descriptors. Never silently pick the first VID/PID match. Without a unique serial, use rig topology plus interface, verify identity after reconnect, and require reselection when ambiguous.

SCPI mode · first delivery

Mutate commands and binary-block data, then construct valid USBTMC framing. Use known queries and application commands as seeds. Non-query writes do not imply a response.

Seeds: *IDN?\n, SYST:ERR?\n, valid application queries, and valid/truncated :DATA:WRITE #… blocks.

Raw protocol mode · next delivery

Mutate selected header or payload regions in named sequence templates. Raw writes preserve malformed bytes: do not repair tags, inverse tags, lengths, EOM or padding after mutation.

Operation scaffold, host buffers and deadlines remain validated. Initial sequence variants are explicit templates, not a new general-purpose language.

Sequence example

1. Write partial command with EOM=false.
2. Request response with a bounded read size.
3. Record response, timeout or stall.
4. Execute the template's explicit USBTMC clear handshake.
5. Write a valid *IDN? message with EOM=true.
6. Request and verify identity response.
7. Sample MCU state, save evidence, decide whether to stop.

Operations belong in the harness: logical write, exact raw bulk write, request/read, bounded delay and specific USBTMC class requests. Verify request fields against the specification before implementation. Class clear, endpoint halt clearing and USB device reset are distinct operations.

Per-case ordering

  1. Acquire interface and debug leases; open hardware.
  2. Preflight a known query and MCU observation.
  3. Generate bytes with the existing mutation path.
  4. MonitorSetHarness samples before, executes the sequence, then samples after.
  5. Persist exact transfers, responses and monitor evidence.
  6. Stop on unusable protocol state or MCU failure; release resources.
Preserve evidence before recovery. No implicit endpoint clear, reply draining or board reset before recording a failure. Clear/abort inside a test is an explicit stimulus. Initial MCU policy is stop. Recovery between campaigns is a separate recorded action.

Outcome classification

ObservationClassificationAction
Invalid command returns a documented errorExpected rejectionContinue if subsequent communication is healthy.
Mutant times out; valid canary succeedsNo reply / inconclusiveRecord; do not label an MCU crash.
Valid canary fails while CPU remains runningProtocol failure / unavailable interfaceStop and preserve transcript.
Persistent fault or lockup in MCU monitorMCU crash evidenceExisting fault snapshot; stop and save.
Disconnect or unexpected resetDisconnect/reset evidenceStop; verify identity before reconnect replay.
Host rejects invalid sequence settings before I/OInvalid test configurationDo not count as firmware coverage or a firmware bug.

A canary following incomplete input is meaningful only after explicit synchronization. Waiting for more bytes can be legitimate. Bracketing MCU observations does not prove which step caused a transient failure.

Evidence and reproduction

  • Campaign manifest: normalized config, firmware identity, descriptors, monitor config, generator seed, initial baseline and software revisions.
  • Case: existing content-hashed input, campaign ID/index, effective sequence template and mutated region.
  • Transcript: ordered bulk/control operations; exact bytes; requested/actual lengths; relative timestamps; replies and exceptions.
  • Result: protocol classification, existing HarnessResult fields, MCU verdicts and snapshots.
  • Replay uses the same harness with mutation disabled and an explicitly selected, verified target. Preserve earlier campaign artifacts.

Payload hash alone is not sequence identity. The same bytes with different EOM, operation order or delays are different tests. Store the effective sequence with campaign attribution.

Resource and execution bounds

  • Proposed key: usbtmc:1209-0001-SHA256(serial)/if0; separate from the debug key. Python/Rust same-host takers use identical normalization.
  • Hold the lease for the connection lifetime. Claim only the selected USBTMC interface, not the composite vendor log interface.
  • Release on failed setup, cancellation and completion. Restore a driver only if this session detached it.
  • Bound operation count, actual transmitted bytes, delays, reads and case deadline. Fuzzed declared lengths must not cause unbounded host allocation.
  • Check cancellation between operations; transfer deadlines bound cancellation latency.

5. Phased implementation plan

Phase 0 · Establish the baseline
  • Choose board/firmware, rig interface and independent debug probe.
  • Record descriptors and valid USBTMC traffic; verify PyUSB/libusb access and MCU manual check.
  • Audit API/model serialization, enum switches and existing lock-key construction.
  • Confirm metadata duplication before planning its removal.

Exit: repeatable identity query and MCU observation; agreed wire and lease contracts.

Phase 1 · Real backend protocol support
  • Add adapter and harness with valid framing and bounded response handling.
  • Compose hardware and leases at the existing application boundary.
  • Add protocol metadata, choices/migration, live rig discovery and real connection checks.
  • Preserve settings and reject USBTMC mock fallback.
  • Verify cleanup on failed open, stop and cancellation.

Exit: backend sends real queries, records replies, reports missing/busy hardware and releases the interface.

Phase 2 · Complete application workflow
  • Add USBTMC picker/config to existing UI and round-trip saved settings.
  • Add SCPI/binary seeds through current case management.
  • Extend result evidence/logger and exact replay path.
  • Show protocol failures separately from MCU evidence.
  • Make desktop Device Control honor the same-host USB lease.

Exit: operator configures, runs, inspects and replays a real campaign from the application.

Phase 3 · USBTMC headers and state sequences
  • Add raw frames and validated class-request operations.
  • Add templates for split messages, EOM changes, tags, lengths, padding and read sizes.
  • Test clear/abort during partial commands and pending replies.
  • Place canaries after explicit synchronization; retain exact transcripts.
  • Replay every interesting finding from its verified baseline.

Exit: malformed frames reach firmware unchanged; saved failures reproduce or are explicitly reported as flaky.

Phase 4 · Triage, fixes and optional native fuzzing
  • Reduce findings by deleting operations and shrinking byte regions.
  • Locate owner: TinyUSB, glue, SCPI core or application handler.
  • Fix the owner and retain minimal regression reproductions.
  • Optionally add native sanitizer fuzzing around existing C tests and TinyUSB stub.
  • Consider automatic recovery only after evidence and reconnect behavior are verified.

Exit: accepted bugs have a reproducible case, owner, fix and verification evidence.

7. Risks and limits

  • Bus addresses change after resets; reconnect must verify identity.
  • Raw USB transfers provide message and class-request control, not arbitrary electrical/link-layer packets.
  • Logical replay cannot guarantee identical physical scheduling; keep flaky findings separate.
  • Mutation plus MCU observation is black-box hardware fuzzing, not firmware coverage feedback.
  • Before/after samples may miss transient faults; start with short sequences.
  • Initial platform acceptance is Linux; qualify Windows/macOS driver binding and lock behavior separately.
  • Keep existing CAN/UART/SPI behavior, monitor plugins and Device Control working.
