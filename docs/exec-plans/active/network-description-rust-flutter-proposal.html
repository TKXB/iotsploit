01 · Decision & scope

Make the document the primary object.

The user has selected a separate Rust + Flutter file explorer. The proposed first release is a tool inside the existing IoTSploit app, with its own route and document lifecycle. Opening a file requires neither a target ID nor a display name. Creating a target remains an explicit, separate operation.

Optional next delivery: “Create Target” converts either a parsed DBC or a parsed ARXML document to the existing target contract and submits it through the existing creation service. It must not become a prerequisite for browsing. DBC conversion creates a new target; the Python CLI's existing-target merge behavior is retained separately.

Success: launch the app without Django, open a supported DBC or ARXML, inspect its frames and signals, follow references, review limitations, and close it. No target is created or selected.

04 · Proposed architecture

Rust owns source meaning. Flutter owns interaction.

The new document core depends on source parsers and reusable CAN definitions. can-core does not depend on the document viewer, Django, Flutter, or AUTOSAR. Flutter obtains display data through the bridge and keeps selection, sorting controls, and navigation state.

Avoid a universal replacement model: store source-specific details alongside shared communication views. ARXML PDUs, references, and packages must not disappear simply because DBC has no equivalent.

05 · User experience

A document explorer, available before any target exists.

  1. Open Toolkit → Network Descriptions. Reuse the toolkit catalog and availability rules.
  2. Choose Open DBC or Open ARXML. First release opens one source per document. Multi-file ARXML is a later extension; unrelated DBCs are not merged into one invented network.
  3. Show loading stages: reading, parsing, resolving references, building indexes. Only show numeric progress if the underlying operation exposes real progress.
  4. Show document summary, source files, supported-feature status, and counts. Open the outline and initial table.
  5. Select a node, frame, PDU, or signal; inspect properties and source identity. Follow references to their definitions. Unresolved links explain which reference could not be found.
  6. Close the document to release its resources. Changing the current target has no effect on the open file.

Views and interactions

Reuse the existing outline/table/inspector visual language and shared app components. Offer a network topology graph where the document actually defines topology. Show frames and signals in tables, with a bit-layout view only when the existing codec can represent the selected signal faithfully. Source properties mean the retained parsed representation; exact source snippets require retained bytes and available spans.

On narrow screens, show outline and details sequentially. Rust handles filtering/sorting for large result sets before pagination. A result selection has a stable document entity ID, so navigating from a reference selects the same entity in every view.

Coverage must be visible. Distinguish malformed input, unresolved references, valid but unsupported semantics, and information unavailable in the source. A successful XML parse alone must not show “fully supported.”

Keep browsing fidelity separate from codec capability

Reuse FrameDef and SignalDef for layouts they accurately express. Add source metadata and richer mappings in the document owner. If a signal cannot fit the current codec—wide integers, floating-point payloads, complex multiplexing—display its actual definition and mark the codec action unavailable. Do not silently narrow it.

Prefer a Rust-owned opaque document containing its native model and compact indexes. Build bounded summaries/details on demand rather than retaining a second full object graph of every source element. Share definitions by ID; frame placement is its own relation.

07 · Parser strategy

Reuse DBC. Evaluate a proper AUTOSAR foundation.

DBC: extend the existing Rust owner

Start with can-core::parse_dbc. Preserve declared nodes without frames, node comments, senders, signals, choices, and warnings through the document API. Replace the unused can_parse_dbc bridge and its now-unused mapping/types rather than keeping a second interface.

DBC ownership during migration: Rust owns new local-viewer format work. Python dbc.py::parse_dbc remains the compatibility implementation for apply_dbc, the import CLI, and its fuzz target until Phase 5 explicitly migrates those consumers. The parser implementation owner maintains a single versioned feature matrix and shared synthetic input set. Every Rust change reruns comparisons for the common supported subset; newly supported Rust-only constructs are marked as differences and unavailable through Python, not silently advertised as equivalent. Avoid independently expanding Python's grammar; any necessary legacy fix is reviewed against both implementations.

Audit float types, extended multiplexing, signal/frame comments, receivers, attributes/defaults, CAN FD metadata, escaped strings, and source encodings. Those are coverage checks, not claims of current support. For the first viewer, unsupported meaningful records must be reported rather than silently discarded.

If corpus evidence shows the current line parser cannot cover the agreed scope cleanly, evaluate replacing its internals with can-dbc, whose documentation lists a broader DBC grammar. Keep the existing parser entry point and downstream behavior where compatible. Do not operate two competing Rust parsers in production.

ARXML: load the AUTOSAR model, then extract communication meaning

Evaluate autosar-data first: its documentation describes multi-file loading, AUTOSAR paths, cross references, validation, and non-strict loading. Evaluate autosar-data-abstraction only where it removes complex traversal; it provides common communication abstractions but explicitly does not cover every class, including LIN in its listed bus abstractions.

These capabilities make the crates candidates, not a proven drop-in replacement for cantools. Confirm schema support, reference behavior, encoding acceptance, thread/FFI compatibility, dependency licensing, memory profile, and required communication constructs on the project corpus before pinning versions.

Named licensing constraint

The ui/can workspace declares GPL-3.0-or-later OR LicenseRef-IotSploit-Commercial. To preserve the commercial distribution option, this proposal requires new parser dependencies and their transitive dependencies to offer an acceptable permissive license; a GPL-only dependency is outside this design. Upstream manifests currently declare MIT OR Apache-2.0 for autosar-data, autosar-data-abstraction, and can-dbc. Before adoption, record the exact pinned versions, transitive license inventory, selected license terms, and notice/attribution requirements. Upstream main-branch declarations alone are not a release audit.

09 · Bridge & lifecycle

One document handle, small query results.

Use the app's existing flutter_rust_bridge integration. Keep CPU-heavy parsing on the Rust worker side, away from Flutter's UI thread. A synchronous Rust parser can be exposed as an asynchronous Dart call; adding async fn alone does not make CPU work non-blocking or cancellable.

// Illustrative API shapes; finalize after the parser feasibility phase.
open_document(sources: Vec<DocumentSource>) -> DocumentHandle
document.summary() -> DocumentSummary
document.children(parent, offset, limit) -> Page<TreeEntry>
document.search(query, scope, offset, limit) -> Page<SearchHit>
document.frames(network, filter, sort, offset, limit) -> Page<FrameRow>
document.details(entity_id) -> EntityDetails
document.references(entity_id, offset, limit) -> Page<ReferenceRow>
document.diagnostics(offset, limit) -> Page<Diagnostic>
// Closing releases the opaque owner and any document-owned source resources.

DocumentSource accepts a local path when usable or explicitly supplied bytes with a display name when the platform requires them. Detect format from content and report mismatched extensions. Do not pass a full source as a Dart string when Rust can read it directly.

  • Ownership: page/session owns an opaque document. Prefer bridge-managed lifetime; avoid a global ID registry. Clear Dart references and verify eventual native release when closing.
  • Query bounds: cap page size in Rust; filter and sort before slicing. Return totals or a continuation indicator without materializing all rows in Dart.
  • Thread safety: verify the native model can safely cross the bridge boundary. Keep a completed document read-only and coordinate queries in its owner if required.
  • Failure: structured fatal error for invalid input; partial document plus diagnostics only when the source can be loaded meaningfully. Never return an empty “successful” document after a parse failure.
  • Cancellation: support checks between owned stages. An underlying parser may not be interruptible mid-call; document that limit and release its result when it finishes. Do not claim immediate cancellation.
10 · Resources & platforms

Large-file behavior must be measured end to end.

The current Python importer permits files up to 256 MiB. That is an existing upload contract, not proof that a 256 MiB AUTOSAR document will fit safely in the app. Determine local per-file and total-document limits from measured native-model memory, indexes, retained bytes, and bridge results.

Platform rollout

Linux desktop: first end-to-end acceptance platform on this rig. Windows/macOS: target local file paths, with release gated on native builds and file lifecycle checks. Android/iOS: validate file-picker URI/byte handling, memory limits, and library build compatibility before enabling. No speedup ratio, memory budget, fixed parse deadline, or delivery date is asserted here. Set those targets after Phase 0 measurements. Keep unsupported platforms clearly unavailable through existing capability rules.
